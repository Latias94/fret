# Findings - 2026-05-21

## F242: Desktop repeating timers no longer starve diagnostics redraw delivery

Layer: desktop runner scheduling plus launched diagnostics script liveness.

Status: mechanism defect fixed. The broad `ui-gallery-shadcn-runtime-evidence` suite is unblocked
again.

What was found:

- The RadioGroup checked-state slice promoted a new broad-suite member, but the broad suite could
  fail earlier in `ui-gallery-command-retained-active-descendant-action-state.json` with
  `script_stalled_no_frames` while the script was waiting for `scroll_into_view` progress.
- Focused repros showed the script had already injected wheel/pointer work and requested redraws,
  but the launched native runner could remain inside the same effect-drain turn without returning
  to winit to deliver the requested `RedrawRequested`.
- The owning-layer defect was in desktop repeating timer scheduling. `fire_due_timers(now)` rearmed
  repeating timers from the stale drain-turn `now`. If a diagnostics keepalive timer did enough
  work, the timer could already be overdue again before the next fixed-point drain iteration. That
  allowed the same repeating keepalive timer to catch up repeatedly inside one runner tick and
  starve the platform frame it had just requested.

What was changed:

- `TimerEntry` now records `last_fired_tick`, and `fire_due_timers` skips a repeating timer that
  already fired during the current runner tick.
- Repeating timers are rearmed from handler completion time in `finish_fired_timer`, not from the
  stale pre-handler drain timestamp.
- Asset-reload polling timers use the same timer-entry initialization path.
- Diagnostics no-frame keepalive paths now preserve redraw/RAF intent for effect-only,
  keyboard/text/IME, and pointer-move injection paths. `wait_frames` keepalive ticks may drain an
  already-started wait counter without skipping the real next script step.
- Script start and effect-only waits now enqueue an explicit redraw plus RAF, and the UI app driver
  bridges script-injected command flushes back into a post-flush frame request.

## F243: Runner timer scheduling now has a synthetic overlap stress gate

Layer: desktop runner scheduling tests.

Status: focused regression coverage added. No additional runtime defect was reproduced after F242;
this slice turns the discovered class into a cheap owning-layer gate.

What was found:

- F242 proved the real launched diagnostics failure through UI Gallery, but the cheapest regression
  test still covered only one repeating timer at a time.
- The risk class is broader: a diagnostics keepalive timer and a windowless asset-reload-style poll
  timer can both be overdue in the same stale drain turn. The invariant must hold for overlapping
  timers, not only for one token.

What was changed:

- Added `overlapping_repeating_timers_do_not_catch_up_inside_one_runner_tick`.
- The test primes two overdue repeating timers: one window-targeted timer representing script
  keepalive and one windowless timer representing asset-reload polling.
- After the first fire, the test deliberately makes both deadlines stale again before advancing the
  runner tick. `fire_due_timers` must return `false` for the second same-tick call, then fire both
  timers again only after `tick_id` advances.

Evidence anchors:

- `crates/fret-launch/src/runner/desktop/runner/timers.rs`.

Run results:

- Focused stress gate:
  `cargo test --profile dev-fast -p fret-launch overlapping_repeating_timers --lib -- --nocapture`
  - Result: passed; 1 test.
- Full runner timer regression filter:
  `cargo test --profile dev-fast -p fret-launch repeating_timer --lib -- --nocapture`
  - Result: passed; 3 tests.

Next slice recommendation:

- With the timer starvation class covered at the owning layer, move back to harness discovery. A
  good next target is retained relation/action-state mutation outside Command/RadioGroup, or a
  layout/paint/hit-test split where cached visuals can pass while semantic/action metadata drifts.
