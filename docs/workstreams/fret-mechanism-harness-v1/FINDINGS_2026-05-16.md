## F109: Cross-root anchored fixture found a recipe-layer root-boundary gap

Layer: `fret-ui` mechanism harness, `fret-ui-kit` overlay policy helpers, and shadcn anchored
overlay recipes.

Status: fixed for the synthetic and focused recipe gates. The remaining uncovered surface is a
runtime UI Gallery or focused diagnostics gate that exercises a real secondary viewport or embedded
root.

What was found:

- The new `anchored_cross_root_coordinate_v1.json` fixture proved that core `AnchoredProps` can
  resolve an anchor element from another render root and place against a non-window overlay/root
  boundary. No core `fret-ui` coordinate-conversion defect was reproduced by this synthetic slice.
- The fixture schema rejected the proposed `root-boundary` domain label, so the suite now uses the
  existing `overlay` and `layout` domains.
- A real policy-layer gap was found in `fret-ui-kit::overlay`: the public anchored placement helpers
  documented root-local placement but still derived the collision/clamp outer rect from
  `environment_viewport_bounds`. That is harmless for full-window roots, but it is wrong for
  embedded or secondary render roots where the owner/source root is not the OS window.
- The same pattern existed across shadcn anchored overlay families. Popover, Select, Tooltip,
  HoverCard, DropdownMenu, ContextMenu, and Menubar were relying on the environment viewport for
  anchored collision boundaries rather than the current render root bounds.

What was fixed:

- Added `root_bounds_for_placement` and `outer_bounds_with_window_margin_for_root` to
  `ecosystem/fret-ui-kit/src/overlay.rs`.
- Updated `anchored_panel_bounds_for_element` and `popper_layout_for_element` to use current render
  root bounds while still observing the environment viewport for metric invalidation.
- Switched shadcn Popover, Select, Tooltip, HoverCard, DropdownMenu, ContextMenu, and Menubar
  anchored placement paths to the root-boundary helper.
- Added a focused `fret-ui-kit` gate proving the root-boundary helper uses `ElementContext::bounds`
  for a non-zero root origin.
- Added the `fret-ui` synthetic fixture and harness for cross-root anchor/overlay coordinate
  conversion.

## F110: Runtime multi-viewport Combobox gate found a mechanism-layer root-boundary cache gap

Layer: `fret-ui` layout/runtime cache, `fret-ui-kit` overlay policy helpers, shadcn anchored overlay
recipes, and UI Gallery diagnostics.

Status: fixed for the resizable multi-viewport Combobox runtime gate.

What was found:

- The new UI Gallery Resizable multi-viewport Combobox gate reproduced the remaining high-risk
  runtime gap from F109: the trigger lived near the bottom of a Resizable panel viewport root, the
  OS window still had room below it, and correct placement had to flip against the panel viewport
  rather than the window.
- The first run failed at `wait_overlay_placement_trace`: the trace chose `bottom`, reported
  `outer_collision=900x1000@0,0`, and treated the window as the collision boundary.
- The underlying mechanism defect was not `AnchoredProps` coordinate conversion. The runtime
  `ElementContext::root_bounds_for_element` query used `NodeEntry.root` as a declarative owner root.
  For descendants inside `LayoutCx::layout_viewport_root`, that owner root can remain the outer
  render root even though the element's effective boundary is the nearest layout viewport root.

What was fixed:

- Added a per-element effective root-boundary cache in `WindowElementState`.
- Rebuilt that cache after final layout from live element-node mappings and the nearest registered
  `viewport_root`, while leaving `NodeEntry.root` as the declarative owner-root contract.
- Updated both `ElementContext::root_bounds_for_element` and the free
  `elements::root_bounds_for_element` query to prefer the effective per-element boundary before
  falling back to owner root bounds.
- Added a focused mechanism test that keeps `NodeEntry.root` pointed at an outer owner while the
  element's node is under a registered viewport root.
- Added a focused view-cache hit test that reuses the cached declarative subtree while moving the
  same element between viewport roots, proving the effective boundary cache rebuilds even when the
  subtree render function is not re-entered.
- Removed the temporary `FRET_DEBUG_OVERLAY_ROOT_BOUNDS` stderr hook after structured placement
  traces proved the fix.

## F114: Command-gated Switch driver dispatch trace was missing

Layer: UI Gallery runtime driver, diagnostics trace recording, and shadcn Switch command-gated
action-state surface.

Status: fixed for the focused runtime gate; no new recipe defect reproduced. The gap was harness
observability in the UI Gallery driver.

What was found:

- The first F114 runtime pass failed at `wait_command_dispatch_trace_timeout`. The trace for
  `ui_gallery.switch.command_gate.toggle_enabled` existed, but it was recorded as `handled=false`,
  so the script could not observe a driver-handled event.
- The Switch command path itself was fine: it updated `WindowCommandEnabledService`, refreshed the
  model, and requested redraw. The missing piece was diagnostics bookkeeping in
  `apps/fret-ui-gallery/src/driver/runtime_driver.rs`.
- That left a blind spot in the harness. A command owned by the gallery driver could bubble through
  `UiTree` as unhandled and still never emit a second `handled_by_driver=true` dispatch decision,
  so the runtime script could not distinguish "ignored" from "handled by driver".

What was fixed:

- Added a driver-handled dispatch record for the owned Switch command-gate toggle path in
  `apps/fret-ui-gallery/src/driver/runtime_driver.rs`.
- Kept the pending command source stable so the driver-handled trace reuses the same origin metadata
  that the bubbling path recorded.
- Left the runtime gate strict. The script still requires the actual handled trace instead of
  falling back to a weaker proxy.
