## F263: HitTestOnly stale path-cache coverage needed runtime promotion, not a new mechanism fix

- F262 recommended returning to retained/cached root-boundary surfaces, especially paint-cache
  replay, hit-test cache, and stale metadata across detach/reattach.

  higher-z siblings, and dispatch-level pointer moves, but the runtime UI Gallery gate only proved

## F264: Provider-sensitive ViewCache state needed an explicit cache-key contract and Direction runtime suite

Context:

- F263 recommended staying on retained/cached root-boundary stale-state risk after promoting the
  HitTestOnly stale path-cache runtime row.
- Direction/RTL behavior currently lives in recipe/provider policy surfaces (`DirectionProvider`,
  `PortalInherited`) rather than a general `fret-ui` writing-mode/layout primitive contract.

What was found:

- No new `fret-ui` mechanism or shadcn recipe defect was reproduced.
- The real gap was contract durability: provider-style inherited state was not recorded in the
  ViewCache lifecycle fixture, so future DirectionProvider-sensitive cache roots could accidentally
  assume provider state is an implicit cache dependency.
- The correct current contract is explicit: provider-sensitive recipes must carry the provider value
  in `ViewCacheProps::cache_key` when a provider change should rebuild the cached subtree. An
  unkeyed provider-sensitive cache keeps replaying the first rendered subtree.
- The Direction docs smoke script existed but was not promoted into a dedicated suite or protocol
  roundtrip gate.

- Added provider-state cases to `view_cache_lifecycle_v1.json` and the lifecycle harness:

## F266: Cached Combobox relation-bounce exposed over-broad viewport-root cache ownership

Context:

- F265 recommended moving from retained row metadata into a cached overlay/root-boundary relation
  gate where stale relation edges can survive visual success.
- Resizable multi-viewport Combobox already had placement coverage, but the cached-source moving
  path did not assert the `controls`/`labelled_by` relation lifecycle across close, move, and reopen.

What was found:

- The new cached-source relation-bounce gate passed, but refreshing the full `ui-gallery-resizable`
  suite exposed a real `fret-ui` mechanism regression in the existing multi-viewport Combobox row:
  the overlay placement trace chose `bottom` against the 900x1000 window outer bounds instead of
  flipping to `top` against the right Resizable panel bounds.
- The root cause was an ownership bug in the cross-frame element root-bounds cache. Cached
  viewport-root bounds were retained or pruned using the whole layer root as the owner. An ancestor
  or overlay frame could therefore drop a still-valid panel viewport boundary even though the widget
  that registered the viewport root did not relayout.
- The correct ownership unit is the direct parent that registered the viewport root. If that owner
  relayouts and no longer registers the viewport root, prune. If only an ancestor, overlay, or
  unrelated sibling relayouts, preserve the previous viewport root bounds for descendants.

What was changed:

- `WindowElementState` now stores element root-bounds records with the viewport root node and its
  registration owner, not only the rect.
- `sync_element_bounds_cache_after_layout` carries forward previous descendant root-bounds entries
  across fast-path, overlay-only, and ancestor-only frames, while still pruning when the viewport
  registration owner relayouts without registering that root.
- Added focused `viewport_roots` tests for fast path, overlay-only, retained overlay parent,
  ancestor-only relayout, owner-prune, nearest-root, movement, and view-cache-hit movement cases.
- Added `ui-gallery-resizable-view-cache-moving-combobox-relation-bounce.json` and promoted it into
  `ui-gallery-resizable`, proving cached Combobox relation endpoints are gone while closed, become
  valid on reopen, and still use the moved panel root boundary for placement.
