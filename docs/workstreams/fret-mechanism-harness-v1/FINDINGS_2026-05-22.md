## F262: Command disabled active-descendant coverage had promotion/serialization debt, not a new recipe defect

Context:

- F261 recommended returning to Command because it is the main action-state comparison point that
  uses active-descendant/list semantics instead of roving menu focus.
- The codebase already had two strong Command rows: a direct disabled-focusable keyboard
  suppression gate and a retained/windowed active-descendant action-state mutation gate.

What was found:

- No new Command recipe/runtime defect was reproduced. The direct disabled-focusable gate already
  proves the intended invariant: default disabled rows are skipped, opt-in disabled-focusable rows
  can become active descendants, the active disabled row exports `disabled=true` and
  `invoke=false`, and Enter does not dispatch the row action.
- The durable gap was suite and schema coverage. The retained/windowed mutation row was already in
  `ui-gallery-shadcn-runtime-evidence` and had protocol roundtrip coverage, but the direct
  disabled-focusable row was only in the Command and shadcn conformance suites and lacked a
  dedicated protocol roundtrip.
- A first fresh focused runtime run with the default `300000ms` harness timeout timed out while the
  script was still progressing through long Command-page startup/click-stable work; the captured
  bundle showed the target page/input existed and the script was still at step 8. Re-running with a
  larger timeout completed and passed, so this is recorded as harness-time-budget evidence rather
  than a Command failure.

## F263: HitTestOnly stale path-cache coverage needed runtime promotion, not a new mechanism fix

Context:

- F262 recommended returning to retained/cached root-boundary surfaces, especially paint-cache
  replay, hit-test cache, and stale metadata across detach/reattach.
- The mechanism layer already had focused stale hit-path guards for moved cache roots, moved
  higher-z siblings, and dispatch-level pointer moves, but the runtime UI Gallery gate only proved
  successful path-cache reuse and HitTestOnly paint-cache replay.

What was found:

- No new hit-test/runtime defect was reproduced. The existing mechanism correctly rejects a stale
  cached lower-child path when a higher-z sibling moves under the same pointer, falls back to full
  hit testing, and refreshes the cache to the higher-z sibling.
- The durable gap was runtime promotion: there was no UI Gallery surface that created a move-only
  stale-path scenario under a cached root and asserted both a path-cache miss and later path-cache
  reuse.
- A first attempt to run the promoted script against a prebuilt `fret-ui-gallery.exe` failed at
  diagnostics preflight because `gallery-dev` launch features cannot be proven for prebuilt
  binaries. Re-running via `cargo run --profile dev-fast -p fret-ui-gallery --features gallery-dev`
  passed; this is launch hygiene evidence, not a runtime failure.

What was changed:

- Extended the hidden HitTestOnly Paint-Cache Probe page with a cached-root stale-path surface:
  the lower target's first pointer-move handler moves a higher-z cover over the same point, while a
  status label records the last routed hit.
- Added `ui-gallery-hit-test-only-stale-path-cover-move.json`, which disables the hit-test bounds
  tree, sweeps the target, waits for `stale_path_hit=cover`, and gates
  `hit_test_path_cache_misses_ge(min=1)` plus `hit_test_path_cache_hits_ge(min=1)`.
- Added protocol roundtrip coverage and promoted the script into the
  `ui-gallery-hit-test-only-paint-cache` suite.
- Refreshed `tools/diag-scripts/index.json`; registry metadata now lists both HitTestOnly
  paint-cache rows in the dedicated suite.
