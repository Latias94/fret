# Findings 2026-05-12

## F4: WindowMetricsService environment changes did not reach view-cache environment dependencies

Layer: `crates/fret-ui` declarative runtime / environment mechanism

Status: fixed

What was found:

- Existing environment view-cache tests mostly wrote directly into `ElementRuntime`, while real
  desktop/web runners write platform environment updates into `WindowMetricsService`.
- `render_root` only synchronized viewport bounds, scale factor, safe-area insets, and occlusion
  insets from `WindowMetricsService` into `ElementRuntime`.
- As a result, view-cache subtrees that queried color scheme, reduced motion, text scale, reduced
  transparency, accent color, contrast preference, or forced-colors mode through the real
  `WindowMetricsService` path could incorrectly stay cache-hit after the environment changed.

How it was exposed:

- Added a fixture-driven environment view-cache harness:
  `crates/fret-ui/src/declarative/tests/fixtures/environment_view_cache_invalidation_v1.json`
- Added a thin declarative runner:
  `crates/fret-ui/src/declarative/tests/environment_view_cache_harness.rs`
- The first run failed before the runtime fix:
  - `renders.env_cache` stayed at `1` instead of `2`.
  - `observed.env_unique_values` stayed at `1` instead of `2`.
  - Failures covered reduced motion, color scheme, contrast preference, forced colors, text scale,
    reduced transparency, and accent color.

What was fixed:

- `crates/fret-ui/src/declarative/mount.rs` now commits all known `WindowMetricsService`
  environment values into `ElementRuntime` before declarative rendering:
  - prefers reduced motion,
  - text scale factor,
  - prefers reduced transparency,
  - accent color,
  - color scheme,
  - contrast preference,
  - forced colors mode,
  - plus the existing scale factor, safe-area, and occlusion paths.

Regression coverage:

- Fixture suite:
  `crates/fret-ui/src/declarative/tests/fixtures/environment_view_cache_invalidation_v1.json`
- Fixture runner: `crates/fret-ui/src/declarative/tests/environment_view_cache_harness.rs`
- Existing focused environment tests: `crates/fret-ui/src/declarative/tests/environment_queries.rs`
- Runtime commit point: `crates/fret-ui/src/declarative/mount.rs`
- Real source path: `fret_core::window::WindowMetricsService`

Run results:

- `cargo test --profile dev-fast -p fret-ui --lib mechanism_harness_environment_view_cache_invalidation_matches_oracles -- --nocapture`
  - Before fix: failed for 7 cases.
  - After fix: passed, 1 test.
- `cargo test --profile dev-fast -p fret-ui --lib environment_ -- --nocapture`
  - Result: passed, 12 tests.
- `cargo test --profile dev-fast -p fret-ui --lib view_cache -- --nocapture`
  - Result: passed, 58 tests.
- `cargo fmt --package fret-ui --check`
  - Result: passed.

Next slice recommendation:

- Move to hit-test/routing or overlay/focus next. The environment slice shows the harness is now
  capable of finding real mechanism bugs when it drives the same entry point as runners instead of
  direct internal state.

## F5: Pointer occlusion and captured-pointer routing needed fixture-level observability

Layer: `crates/fret-ui` tree input routing / overlay mechanism

Status: covered, no runtime fix required

What was found:

- Existing focused tests covered pointer occlusion, outside-press observers, pointer-move observers,
  modal barrier wheel scoping, and captured-pointer behavior.
- The coverage was procedural and spread across multiple files, so the workstream coverage map still
  could not answer whether pointer occlusion and captured-pointer routing were covered as a
  reviewable matrix.
- The first fixture run also exposed a harness schema constraint: `domains` is a fixed mechanism
  enum, not a free-form tag list. Specific subdomains such as pointer occlusion and pointer capture
  must be represented by suite/case ids and docs unless the shared schema is intentionally extended.

What was added:

- Fixture suite: `crates/fret-ui/src/tree/tests/fixtures/pointer_occlusion_routing_v1.json`
- Thin tree runner: `crates/fret-ui/src/tree/tests/pointer_occlusion_routing_harness.rs`

The fixture matrix covers:

- `BlockMouseExceptScroll` suppressing underlay move/down dispatch while allowing wheel routing,
- `BlockMouse` suppressing underlay wheel dispatch,
- hit-test-inert modal barriers blocking underlay wheel routing,
- outside-press observer dispatch while underlay pointer-down dispatch is suppressed,
- pointer-move observer dispatch while underlay pointer-move dispatch is suppressed,
- captured underlay pointers suppressing unrelated overlay pointer-move observers,
- captured overlay pointers continuing to receive moves while uncaptured pointers remain occluded.

Run results:

- `cargo test --profile dev-fast -p fret-ui --lib mechanism_harness_pointer_occlusion_routing_matches_oracles -- --nocapture`
  - First run: failed due to invalid fixture `domains` values.
  - After schema-aligned fixture update: passed, 1 test.
- `cargo test --profile dev-fast -p fret-ui --lib pointer_occlusion -- --nocapture`
  - Result: passed, 11 tests.
- `cargo test --profile dev-fast -p fret-ui --lib pointer_move_layers -- --nocapture`
  - Result: passed, 3 tests.
- `cargo test --profile dev-fast -p fret-ui --lib mechanism_harness_hit_test_routing_matches_oracles -- --nocapture`
  - Result: passed, 1 test.

Next slice recommendation:

- Continue into overlay/focus. The pointer routing slice shows that event-routing facts need
  first-class mechanism metrics; overlay/focus should use the same pattern for focus trap, restore,
  roving focus, active descendant, modal barrier, and nested overlay interactions.

## F6: Focus barrier routing needed a fixture-level matrix before policy-level focus traps

Layer: `crates/fret-ui` tree focus routing / overlay mechanism

Status: covered, no runtime fix required

What was found:

- Existing focused tests already covered hit-test-inert focus barriers, focus traversal under a
  focus barrier, and focus scopes.
- The workstream still lacked a fixture matrix for the tree-level focus substrate that recipe-layer
  focus traps and restore policies depend on.
- The first runner attempt exposed a type-boundary issue: fixture command strings cannot be borrowed
  directly into `CommandId::from`, because these command ids are represented by static command
  values in the tested path.

What was added:

- Fixture suite: `crates/fret-ui/src/tree/tests/fixtures/focus_barrier_routing_v1.json`
- Thin tree runner: `crates/fret-ui/src/tree/tests/focus_barrier_routing_harness.rs`
- The runner maps fixture commands through a closed enum before constructing `CommandId` values.

The fixture matrix covers:

- hit-test-inert overlays keeping active focus barriers,
- focus barrier activation preserving existing overlay focus,
- underlay focus attempts being rejected while a focus barrier is active,
- `focus.next` / `focus.previous` traversal staying inside the focus barrier when the input barrier
  is off,
- modal overlays reporting both modal and focus barriers,
- timer dispatch not clearing focus inside a hit-test-inert focus barrier.

Run results:

- `cargo test --profile dev-fast -p fret-ui --lib mechanism_harness_focus_barrier_routing_matches_oracles -- --nocapture`
  - First run: failed to compile due to borrowed fixture command strings escaping into `CommandId`.
  - After enum-backed command mapping: passed, 1 test.
- `cargo test --profile dev-fast -p fret-ui --lib focus_barrier -- --nocapture`
  - Result: passed, 8 tests.
- `cargo test --profile dev-fast -p fret-ui --lib focus_scope -- --nocapture`
  - Result: passed, 6 tests.

Next slice recommendation:

- Move from tree-level focus barrier to declarative focus behavior: focus scope fixture coverage,
  focus restore policy surfaces, roving focus, active descendant semantics, and UI Gallery
  overlay/focus diagnostics gates.
